## Reporting a Vulnerability

If you discover a security vulnerability in SENTINEL, please report it responsibly:

1. **Do NOT open a public GitHub issue** for security vulnerabilities
2. **Contact us on Discord**: https://discord.gg/k967Q5q6xZ (use the #security channel)
3. **Or email**: Reach out via Discord DM to the project maintainer

We will acknowledge receipt within 48 hours and provide a detailed response within 7 days.

## Security Model: Zero-Trust Architecture

Sentinel v1.0.0 (Stargenesis) operates as an autonomous CLI tool prioritizing security boundaries and safe execution models. 

### 🕸️ Native Execution for Dynamic Audits (`-audit`)

To interact with target web services dynamically, Sentinel operates using Python's native HTTP libraries.

- **Isolation**: All requests are handled via strict session sandboxes natively within the Python runtime, dropping all 3rd-party execution payloads.
- **Tear-Down**: Ephemeral sessions are instantly destroyed once they return output, ensuring no state leakage between audit targets.

### 🛡️ Local Execution for Static Analysis (`-analyze`)

When analyzing local codebases, the process runs natively on the host machine without Docker out of necessity, but is heavily sandboxed.
- **Strict Boundary Confinement**: The `-analyze` flow canonicalizes paths cleanly using `pathlib` and regex bounds to prevent unintentional inclusion of files operating outside the designated scope boundaries (e.g. blocking `/etc/`, `/root/`).
- **Symlink Protection**: Malicious symbolic links pointing outside the authorized scan directory are actively rejected.

### 🔐 Cryptography and Secrets Management

Sentinel securely manages API keys used for Cloud LLM providers (OpenAI, Gemini, Claude, Groq).

- **Encryption-at-Rest**: All provider API keys are encrypted locally using the **HKDF** (HMAC-based Extract-and-Expand Key Derivation Function) standard. Keys are locked as AES `enc_v2_` ciphertexts utilizing a 256-bit machine-specific salt.
- **Atomic Operations**: Configuration files and logs are written using pure atomic TempFile replacements (`os.replace`) operating under strict `os.umask(0o177)`, permanently closing I/O race conditions and guaranteeing `0o600` POSIX permissions.
- **In-Memory**: Passwords and keys are never logged to the CLI output or the terminal screen.

### 🛡️ Core Defenses

- **Cryptographic Dependency Bootstrapping**: Sentinel no longer trusts `pip` implicitly. At boot, the engine actively computes SHA-256 hashes of critical library files on the live filesystem to prevent supply chain poisoning.
- **Inert Shell Execution**: All 3rd-party tool orchestration was rewritten to bypass OS shell parsers entirely (`shell=False`) alongside rigorous `shlex.quote` filtering.
- **Log Forgery Prevention**: The internal `SecurityFilter` strictly strips `\n` and `\r` carriage returns plus all API keys out of logs, thwarting rogue payload-based log forgery.
- **Cloud Exfiltration Protection**: Invoking `-analyze` with a cloud provider (e.g. Gemini, Claude) halts execution with a prominent privacy warning requiring explicit interactive confirmation before transmitting local source code to 3rd-party servers.

### What We Don't Protect Against

- **Host Machine Execution**: Sentinel's core engine executes natively using Python. Standard host security practices apply.
- **Third-Party APIs**: Any data sent to Anthropic, OpenAI, or Google is subject to their respective data privacy models. For entirely localized intelligence, configure and use the `Ollama` provider natively.
- **LLM Hallucinations**: Final cybersecurity reports generated by the agent represent a synthesis of data and probabilities; findings should always be manually verified by a human expert.
